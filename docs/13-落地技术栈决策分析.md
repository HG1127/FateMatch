# 13 落地技术栈决策分析（2026-09-22）

输入：用户调研的《Vibe Coding 全流程指南》推荐技术栈（下称**指南栈**）。目标：判定本项目（随缘网·交友社区）落地应采用哪套技术栈。

## 一、指南栈清单与其隐含前提

清单：Claude Code + Codex / GitHub / pnpm / TypeScript 严格 / **Next.js（App Router）** / React / Tailwind CSS / shadcn-ui / **Zod** / **Auth.js** / **Neon** / **Drizzle ORM** / Vitest / React Testing Library / **Playwright** / **Vercel（Preview + Production）** / GitHub Actions。

架构特点：Next.js 服务端渲染或静态输出；Server Actions 处理表单；Route Handlers 对外 API；Drizzle + Neon + Serverless PG；Auth.js 统一认证鉴权。
适用场景：SaaS / 数据管理系统、用户平台（OA/ERP）、内容媒体营销平台、数据看板、MVP 快速验证。

**隐含前提**（决定它是否适配本项目）：

1. 部署目标是 Vercel 类 Serverless 平台（无常住进程、函数冷启动、数据库连接走 HTTP 短连接池）
2. 项目新建或重写成本可接受
3. 获客依赖公开搜索（SSR/SEO 是核心收益）
4. 认证需要第三方登录（Auth.js 的强项）

## 二、本项目落地约束盘点

| 约束 | 事实 | 对选型的影响 |
| --- | --- | --- |
| 托管形态 | 平台容器常住服务，对外必须监听 8000，数据端口 7000 有外部代理约定 | 与 Vercel Serverless 模型冲突（前提 1 不成立） |
| 项目现状 | 已完整在线：13 个页面、22 张表、自建账号 + 三档权限、20 单测 + 组件测试 | 重写 = 全量回归风险（前提 2 不成立） |
| 数据库 | 已切 Neon（与指南栈一致） | 指南栈最大组件已对齐 |
| 获客形态 | 私域 / 好友邀请型交友社区 | SEO 非当前主通道（前提 3 暂不成立） |
| 认证需求 | 邮箱密码自建体系已含权限三档，无第三方登录需求 | Auth.js 收益低（前提 4 不成立） |
| 维护形态 | 单人维护 + AI 协作 | 框架强约定的分工收益小 |
| 网络环境 | 容器外网出口偶发抖动 | HTTP 短连接驱动（serverless driver）理论上更长连接更耐抖动，列为候选改进 |
| 成本 | Neon 免费层 + 容器已在付；引入 Vercel = 新账单 + 域名备案议题 | 倾向维持现托管 |

## 三、候选方案

- **A 指南标准栈**：Next.js App Router + Drizzle + Auth.js + Vercel，整体重写后落地
- **B 现状栈**：Vite 单页 + 自建数据网关（原生驱动直连 Neon）+ 自建认证 + 容器常住
- **C 混合演进栈**：B 的骨架不动，逐项吸收指南栈的工程件（已完成：Neon、Zod、Playwright、TS 严格、pnpm、GitHub Actions、Vitest、Tailwind；待定：Drizzle、serverless 驱动）

## 四、维度评分（1–5，加权）

权重：落地成本 .25 / 落地风险 .25 / 维护成本 .15 / 性能与获客匹配 .15 / 生态与指南契合 .10 / 托管与成本匹配 .10

| 维度 | A | B | C |
| --- | --- | --- | --- |
| 落地成本 | 1（13 页 + 数据层 + 认证全重写，估 2–3 周全职） | 5（已在线） | 4（增量补齐，已做完大半） |
| 落地风险 | 2（重写回归面大、迁移双写窗口） | 5（零迁移） | 4（小步可回退） |
| 维护成本 | 4（框架约定强、AI 友好） | 3（自研网关自维护） | 4 |
| 性能与获客 | 5（SSR/SEO） | 2（SPA SEO 弱） | 3（可补 OG/预渲染） |
| 指南契合 | 5 | 3 | 4 |
| 托管与成本 | 2（与容器约束冲突、备案/账单） | 5 | 5 |

评分为决策辅助而非证明；关键差异集中在成本/风险两项（合计权重 .5），A 在这两项结构性落后。

## 五、结论：采用 C

保留现状骨架，指南栈的工程保障件按价值增量吸收。**已完成**：Neon 直连（数据库与指南一致）、Zod 入口校验、Playwright 发布冒烟、TS 严格 / pnpm / GitHub + Actions / Vitest / Tailwind。**不做及理由**：

- Next.js 重写：四个隐含前提均不成立，成本风险结构性过高；触发条件见第六节
- Auth.js：无第三方登录需求，自建体系已含权限三档且测过
- Vercel：托管约束 + 备案 / 账单；容器常住即当前生产
- shadcn-ui：自建组件库已覆盖且风格统一，替换纯耗工时
- React Testing Library：已有 6 例组件测试（Vitest 环境），等价覆盖

**待定（条件触发）**：

- Drizzle ORM：启动大功能开发前做 schema 代码化；纯运营维护期不做
- @neondatabase/serverless（HTTP 驱动）：若网关长连接在外网抖动下成为瓶颈再评估替换原生驱动

## 六、转向 A 的触发条件（存档备查）

满足任意**两条**即启动迁移评估：

1. 公开搜索成为主要获客通道（SSR/SEO 刚需）
2. 脱离本平台独立部署（可用 Vercel / 云函数）
3. 需接入微信 / Google 等第三方登录
4. 维护者增至多人协作（框架强约定的分工收益显现）

迁移顺序（届时）：数据层先行（Neon 已就位，补 Drizzle schema 代码化）→ 认证换 Auth.js → 页面逐页重写，旧单页与新站并行灰度过渡。数据与账号哈希已在 Postgres 标准结构内，迁移资产完备。
