# 10 数据备份同步（Supabase 快照）

> **2026-09-22 停用**：数据层已整体切换到 Neon 直连（见 11），备份改用 Neon 自带的 PITR / 分支能力。本工具的数据源是已冻结的旧库，仅保留作历史参考与旧库重建用途。

## 现行备份体系（Neon 时代，v1.9 起自动化）

- **每日自动备份**：看门狗进程每日 04:30 调度备份脚本（`scripts/neon-backup.mjs`）；看门狗启动时若当日备份缺失且时点已过，30 秒后自动补跑。连接串经环境变量传递，不落盘。
- **产物**（落 `backups/`，已 gitignore）：
  - `db-<日期>.json` —— 数据库全量逐表导出，跳过 `gateway_meta` 密钥表；格式与备份演练脚本一致，可直接用于装回验证；
  - `uploads-<日期>.tar` —— 会员上传附件目录归档（有附件才生成）。
- **保留策略**：各类保留最近 7 份，超期自动清理。
- **恢复路径**：数据库装回见 12（隔离演练逻辑同源）；附件恢复解 tar 回 `uploads/` 即可；Neon 侧 PITR / 分支作为时间点恢复补充（待控制台开启）。
- **恢复演练自动化**（v1.10）：看门狗每周日 04:35 自动跑一次 `scripts/neon-backup-drill.mjs`（生产只读导出 → 隔离装回 → 逐表指纹核对 → 销毁），「备份真的能恢复」由每周自动验证；也可随时手动执行。

以下为已停用的 Supabase 快照方案存档：

定位（2026-09-08 定案）：在线存储仍为应用配套数据服务；用户的 Supabase 作为**异地快照备份**承接，不做整体替换。若日后要整体迁移，以本快照为数据源走迁移流程。

## 工具

`scripts/supabase-sync.mjs`：全量读取数据服务各表 → 打成单份 JSON 快照 → 上传 Supabase 存储桶。

- 密钥只走环境变量：`SUPABASE_URL` / `SUPABASE_ANON` / `SUPABASE_BUCKET` / `PB_ADMIN` / `PB_PASS`；不落盘、不进前端、不进仓库。
- `--dry` 只读本地并打印各表行数与快照体积，不上传。
- 快照形态：`{ generatedAt, collections: { 表名: [行…] } }`；剥离 `tokenKey` 等会话签名字段。
- 上传路径：`<bucket>/suiyuan/snapshot-<时间戳>.json`，重名覆盖（x-upsert）。

## Supabase 侧一次性准备

1. 控制台 Storage 建**私有**桶，建议名 `suiyuan-backup`。
2. SQL 编辑器执行（仅放开该桶的上传与读取，其余不动）：

```sql
create policy "sync-select" on storage.objects for select to anon using (bucket_id = 'suiyuan-backup');
create policy "sync-insert" on storage.objects for insert to anon with check (bucket_id = 'suiyuan-backup');
```

## 运行与核对

- 容器内带环境变量运行；结束后核对控制台对象大小与 `--dry` 打印的表行数一致。
- 频率：按需手动；数据重要节点（活动开赛前、大版本前）各跑一次。
- 恢复：解出快照按表写回数据服务管理通道，遵守 06 的删除护栏，先核对再写。

## 边界

- anon 密钥只用于本同步脚本与桶策略；service role 密钥不进入本容器与前端。
- 容器外网出口不稳定属已知约束（见 00 总览 Gate 3 备注），同步失败重试即可，不影响在线服务。
