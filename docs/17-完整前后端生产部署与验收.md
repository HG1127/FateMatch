# 随缘网：完整前后端生产部署与验收 V1.0

核查日期：2026-10-08。技术架构：React + TypeScript + Vite / Node.js Neon Gateway / Neon PostgreSQL。
保留原 VibeX App ID、Source 编辑器约束和平台集成。

## 一、当前已经实现的前后端链路

- 前端：React Router 按页懒加载，包含认证、我的资料、推荐、互相有意、私信、社区、活动与签到、掌柜控制台、隐私与注销。登录与数据可信闸门在 Store 层统一处理。
- 后端：Node HTTP 网关，auth/profiles/matching/messaging/events/safety/admin 七个独立领域模块，拥有鉴权、输入验证、持久化命令、权限拒绝和审计。
- 数据库：Neon PostgreSQL，关系反馈/推荐曝光/审计数据内部分离；public 生产库迁移必须先备份并单独审批。
- 会员图片：基于用途写入独立持久化目录，HMAC capability URL 访问，不暴露原始文件目录。
- 运维：生产同源静态文件服务 + API、/api/health 存活检查、/api/ready 数据库就绪探针、正式构建 SPA 深链接和静态资源访问保护。
- 测试：Vitest、ESLint、TypeScript/Vite build、Playwright 临时 Neon schema 隔离 E2E。CI 分两条：`.github/workflows/quality.yml`（代码质量）与 `.github/workflows/ci.yml`（生产 Docker 镜像）。

业务闭环：注册 → 成年及资料确认 → 真人推荐 → 自主有意 → 双方 mutual → 真人消息 → 活动/签到 → 本人关系反馈。任何线上行为不能使用模拟真人状态填充。

## 二、分开的两种发布路径

### A. 原 VibeX Source

项目来源是 VibeX dev-container 快照，App ID 以 vibex-local/export-manifest.json 为准。必须先阅读 .vibex/skills/vibex-app-source-roundtrip/SKILL.md。

VibeX Source 上传所选目录和 ZIP 条目必须一一对应：选择 app/src/ 时条目为 App.tsx、components/... 等；选择 app/ 时才上传 package.json、src/...。不能带额外项目根目录层级。上传后检查 written 路径、protected file skips、PATH_FORBIDDEN/INVALID_PATH，再刷新预览并显式发布。

**重要**：上传 VibeX 前端 Source 并不自动部署本项目 Node/Neon Gateway。需要另外验证平台对 /__pb、/api/uploads 的真实代理目标及正式发布版本，不能把预览或源码编辑成功等同于公网前后端上线。

### B. 独立同源前后端

使用 pnpm build 生成 dist/，由 pnpm start:prod 在同一 Node 进程服务 React 构建产物、Neon API、/__pb/api/* 兼容路由和签名图片。

- 路由 /me、/matches/ 等深链接可刷新，HTML 按根 base 解析相对静态资源。
- 缺失 JS/CSS 不回退为 SPA HTML；禁止访问源文件、隐藏路径、越界路径和 dist 之外符号链接。
- /api/health 仅检查进程存活；/api/ready 需要数据库连通且认证初始化完成，部署流量应以 ready 状态为准。
- 生产环境必须验证 Neon 服务端 TLS 证书；外部 HTTPS 由反向代理负责，Node 端口仅在内网/localhost 暴露。

**环境变量：**

| 名称 | 要求 |
| --- | --- |
| NEON_DSN | 仅从 Secret Manager / 受控进程环境注入，不能放入前端、Git、容器镜像或公开文档 |
| UPLOAD_DIR | 独立于 dist 的绝对路径，必须位于持久化磁盘或挂载卷 |
| PORT | 默认 8080 |
| HOST | 默认 0.0.0.0，公网应由 HTTPS 反向代理接入 |
| NEON_SCHEMA | 默认 public |
| SY_ADMIN_EMAILS | 可选的服务端管理员白名单，严禁客户端提权 |
| TRUSTED_PROXY_IPS | 可选；只有可信反向代理的**直接连接 IP** 才能配置，默认不信任任何 X-Forwarded-For |

Node 22 + pnpm 10 的正式构建和运行：

~~~bash
pnpm install --frozen-lockfile
pnpm lint
pnpm test
pnpm build
node --check server/neon-gateway.mjs

# 环境变量由部署系统提前注入
pnpm start:prod
~~~

检查：

~~~bash
curl -fsS http://127.0.0.1:8080/api/health
curl -fsS http://127.0.0.1:8080/api/ready
curl -I http://127.0.0.1:8080/matches/
~~~

## 三、独立容器部署选项

文件：Dockerfile、.dockerignore、compose.prod.yml。

- Docker 镜像用多阶段 Node 22 + pnpm frozen lockfile 构建；运行阶段只携带生产依赖、编译前端和 API 服务代码。
- 运行容器非 root，根文件系统只读、capabilities drop、无需宿主 root 权限；上传图片走命名持久化卷。
- 默认绑定 127.0.0.1:8080，再由受信任 HTTPS 反向代理处理公网 TLS。
- Compose 设置 `init`、退出宽限、进程数限制，并保留非 root、只读根目录及独立持久卷；Dockerfile 的就绪探针随运行时 `PORT` 变化。
- **代理 IP 安全规则**：网关默认只使用 TCP 对端 IP 参与限流和安全审计，忽略客户端伪造的 `X-Forwarded-For`。只有在 `TRUSTED_PROXY_IPS` 中逐个列出直接代理 IP 时，才接收该代理转发的**单一、合法**客户端 IP。代理必须覆盖而不是拼接用户自带的头，例如 Nginx 使用 `proxy_set_header X-Forwarded-For $remote_addr;`；禁止配置通配符。此项已有专门回归测试。
- Compose 读取当前宿主进程中的 NEON_DSN，不在文件中存真实连接串。绝不把备份、uploads、.env、日志或 node_modules 打包到镜像。

~~~bash
# NEON_DSN 必须事先从安全密钥管理配置
docker compose -f compose.prod.yml config --quiet
docker compose -f compose.prod.yml build
docker compose -f compose.prod.yml up -d
docker compose -f compose.prod.yml ps
~~~

当前 Windows Runner 可用 Docker CLI，但 Docker Engine 未启动：Compose 静态配置已通过，**镜像实际构建与运行未验证**，需在目标部署主机验收。镜像构建已加入独立 GitHub Actions Docker Gate；只有工作区更改经审查提交/推送后，该 CI 才能提供真实镜像构建证据。

## 四、数据库和账号数据

当前 public 已存在关系反馈、推荐曝光内部表；**不需要为本轮代码再次迁移生产库**。

新环境首次建库和以后的数据库版本升级，必须按：隔离验证 → 数据库及附件备份 → migration dry-run → 人工审查 → 显式 MIGRATE_FORCE=yes → 只读检查 的顺序处理。任何操作禁止直接覆盖现有 public 业务数据。

详见 docs/16-关系反馈试点验收与发布清单.md。备份可能含高度私密信息，要求安全保管；Git bundle 仅覆盖已提交的历史，不能替代当前未提交源码快照。

现有 Node 网关限流与部分运行计数采用单进程内存，在升级为多个实例之前必须增加跨实例共享限流、幂等锁和状态管理。当前部署按**单实例**验收。
